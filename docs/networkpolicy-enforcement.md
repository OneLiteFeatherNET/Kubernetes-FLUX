# NetworkPolicies are not enforced on this cluster

`feather-core` runs Flannel (`kube-system/kube-flannel`,
`ghcr.io/siderolabs/flannel:v0.28.5`) as its only CNI. Flannel implements pod
networking and ships **no NetworkPolicy controller**, and no policy agent
(Calico, Cilium, kube-router) runs alongside it — verified: `kubectl get pods -A`
matches zero of them.

Every `NetworkPolicy` object in this cluster is therefore inert. It exists in the
API server and is never translated into a packet filter.

**Do not read `kubectl get netpol` as evidence that anything is segmented.**

## The policies that exist, and who put them there

As of 2026-08-03 there are eight, and none of them are declared by this
repository:

| Namespace | Name | Origin | What it *looks* like it does |
|---|---|---|---|
| `flux-system` | `allow-egress` | `flux bootstrap`, in `clusters/feather-core/flux-system/gotk-components.yaml` | default-deny cross-namespace ingress to the Flux controllers |
| `flux-system` | `allow-scraping` | same | allow Prometheus to scrape the controllers |
| `flux-system` | `allow-webhooks` | same | allow inbound webhooks to `notification-controller` |
| `dragonfly` | `dragonfly` | generated by `dragonfly-operator`, `ownerReferences` → the `Dragonfly` CR | restrict 6379 to same-namespace pods |
| `kubeshark-debug` | `kubeshark-{dex,front,hub,worker}-network-policy` | the unmanaged kubeshark install — **not in git** | restrict access to the kubeshark UI and hub |

The four `kubeshark-debug` policies disappear when that install is removed; it is
tracked separately and is not part of this document.

`dragonfly/dragonfly` is the most misleading of the rest — it reads as if the
datastore is namespace-restricted. It is not, and it cannot simply be deleted:
the operator recreates it. The three `flux-system` policies are part of the Flux
bootstrap manifest, which `flux bootstrap` regenerates, so hand-edits there do
not survive.

This repository declares **zero** NetworkPolicies of its own — the only match for
`grep -rln "kind: NetworkPolicy" apps infrastructure helm clusters` is
`gotk-components.yaml`, which is generated. Nothing written here depends on
enforcement.

## What this actually costs

There is no L3 barrier between internet-facing workloads (plane, reposilite,
shlink, uptime-kuma, harbor) and the datastores — MariaDB 3306, CNPG 5432,
Dragonfly 6379, Ceph RGW. A single RCE in any of them has unrestricted reach
across the pod network, and there is no policy-drop telemetry to alert on.

This does **not** put `flux-system/sops-gpg` or the Flux git SSH credential at
network reach. Those are Secrets, gated by RBAC and reachable only through the
API server or a container escape — neither of which a NetworkPolicy would have
stopped.

## Why this is documented rather than fixed

Adding a policy-capable CNI (Calico in policy-only mode, or migrating to Cilium)
touches the dataplane on every node. This cluster has already lost Galera
cluster-wide to a Flannel MTU change once; see
`docs/incidents/`. For a single-tenant cluster with one maintainer and ~30
workloads, the payoff — lateral-movement barriers between namespaces that one
person controls — does not currently justify that risk.

That is a deliberate, revisitable decision, not an oversight. What is **not**
acceptable is reasoning from protection that does not exist, which is what this
document prevents.

Revisit if any of these change:

- the cluster gains tenants who do not trust each other
- a workload starts handling data where lateral movement is a compliance concern
- the CNI is being replaced for an unrelated reason anyway
